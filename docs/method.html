Method

How the experiment works

One model, one set of tasks, one prompt template. Only the <context> block changes from level to level.

The question

When a model writes code in an existing project, how much does the way its context is built matter? The harness gives the same model the same change requests and varies one thing: what it gets to see of the repository. It measures whether the change is correct, whether it reuses the project's existing helpers instead of re-implementing them, whether it breaks anything else, and what it costs.

How coding assistants got their context

In about six years the question "what does the model see of the code?" was answered four different ways: the open file, retrieved snippets, the whole repository, and agents that look for themselves. Each level in this experiment reproduces one of these moments (sources in the table below).

  1. 2020 MayRetrieval-augmented generation: a model answers with retrieved documents in its prompt (Lewis et al.). L4, L5

The levels

L0 to L6 build the context once and the model answers in one reply. L7 and L8 are agents: they start from a small context and use tools to look around before answering. Prompt v4 (the current round) never names the file to change: L1 to L6 still show it as their first context block, while the agents find it themselves.

LevelWhat the model sees
L0The task text only (tier-1 control tasks only): what the model does with no repository at all.
L1The target file.
L2The target file, its direct imports and its test file: what a developer would paste by hand.
L3Every source file in the repository, sorted, with paths. On repo L it doesn't fit the window: NO FIT.
L4The target file and the top 3 files by retrieval (BM25 or embeddings).
L5The target file and the top 8 functions by retrieval, with path, imports, signature, docstring and body. The query is the task text, or up to 5 queries the model writes in a planning call.
L6The target file and a one-line signature of every function and class (L6+docs: plus the first docstring line).
L7The repository's file tree (line counts, how many modules import each file) and tools, at most 15 calls. grep: grep, read_file, find_references. hybrid: plus semantic_search. rich: richer versions of those tools plus read_symbol (definitions by name) and line ranges for read_file. selective: rich plus drop, which removes results the model no longer needs from the conversation.
L8Experimental. A list of every file with the names defined in it (no signatures), read_symbol as the only way to read code (by name or line range; a file asked for whole returns its outline), search tools, drop, and edit / create_file tools that change the repository copy directly. The budget is 15 points, with the points left shown after each turn.

When a change creates a file that doesn't exist yet, every level sees its path (L1 to L6 as an empty target block, L7 and L8 as the same two lines), because a new module's name can't be found in the repository. An ablation arm, reuse_hint, adds one line to the system prompt on L1 and L5: "Prefer reusing existing project helpers over writing new ones." The base prompt never mentions reuse.

Why each level

Most levels reproduce a way context is built in a real product or a published method, so the results say something about strategies people actually use. Two are our own: selective dropping in its live-tail form, and L8. Dates are the first public appearance we know of.

LevelPrecedentWhy it's here

L7 selectiveClearing old tool results from an agent's context, as in Anthropic's context editing (September 2025). Recent work argues the same direction from the other side: Belcak et al. (November 2026) find that later tokens cost more to generate (up to 7× on frontier open-weight models) and that frontier models lose little or no accuracy when an agent's context is kept short by frequent compaction. There the harness compacts the conversation into a lossy recap; here the model itself chooses which results to drop, and dropped code can be read again.Whether an agent that curates its own context reads less without losing what it needs. The agent harness (L7, L8)

  • A budget of 15 calls (L8: 15 points). A call that fails (bad arguments, an unknown tool) costs half and gets an error that says what was wrong; several calls can share a turn. L8's edit, create_file and drop are free, and the edit tools keep working when the points are spent.
  • Every tool's description says what it takes and returns, never which tool to prefer. Nothing in any prompt mentions dead code, decoys or reuse.
  • One more chance at the end: a final reply that is a tool call after the tools were gone, an answer without a usable <file> block (L8: a run that changed nothing), or (L8) a changed file that no longer parses each get one retry. Each run records whether it used one.
  • L8 checks syntax after every edit (the file is compiled, never run) and warns with the line, much as SWE-agent's interface lints edits (Yang et al., 2024); unlike it, L8 keeps the edit, since a change can be made in two steps. No tool runs code: a test-running or code-snippet tool was deliberately left out, because it would let the model execute arbitrary code on the host, and the hidden tests must never be an agent's oracle. The harness does run the model's code when it scores a run (hidden tests, repository tests, patch coverage), a risk accepted for every level.

Rules that keep the comparison fair

  • Only the <context> block varies. System prompt, task text, output format, temperature and the output-token limit are identical at every level.
  • Task text uses product language and never names the helper it needs.
  • Hidden tests live outside the repository and never enter the context.
  • Context is never truncated silently. A prompt that doesn't fit the model's window is recorded as no_fit, a result in its own right.
  • No agent frameworks. Chunking, tokenization, ranking and prompt assembly are the variables under study, so the harness owns them.
  • Every level is implemented as well as it reasonably can be, with no thumb on the scale for or against any strategy.

The repository

shopkit is a synthetic order and inventory service written for this experiment, in three sizes. S is about 2k tokens. M is about 40k tokens and 110 files, standard library only, with its own passing tests; it has 25 planted helpers, about half named in words a task would use and half not, near-miss decoys that fail the hidden tests if used instead, and dead code named like the canonical place, as in real repositories. L is the same shop about a year later: about 169k tokens and 280 files including SQL migrations and HTML templates, old code that keeps old names, more dead code, and five live functions of 200 to 270 lines with a business rule buried in the middle. It is too big to send whole. See Tasks.

What each run records

Outcome
PASS: a valid answer and every hidden test passes. FAIL: a valid answer, but a hidden test fails. No accepted answer comes in three kinds: UNPARSABLE: code is there, but not in the required <file> blocks. ASKED TO EXPLORE: no code; the reply asks to look at the repository first, in prose or as a pretend tool call (a level without tools can't). NO ANSWER: the reply was empty (agents that went silent, often after repeating the same tool call). INVALID: anything else, such as an agent's tool error. OUT OF TOKENS: the answer hit the output-token limit. NO FIT: the prompt didn't fit the context window. Infrastructure errors are never recorded; those runs are redone.
Reuse
Reuse tasks have a hidden test that spies on the needed helper and checks the new code really calls it. Reported apart from correctness, so "correct but re-implemented" stays visible.
Regression check
The repository's own tests after the patch. It catches patches that pass the hidden tests while breaking or deleting code elsewhere.
Visibility
Whether the needed helper was in the context at all: its definition, its full body, or a call site.
Output protocol
ok, bad_format, no_code or tool_request (the model asked to explore instead of answering).
Cost
Input, cached and output tokens, latency and tool calls.
Badges
Exact ones read off the run (no code, retried, syntax error in the patch, dead code used, ...) and automatic ones for what the final answer says (declares completion, claims it verified, notes missing context, ...), matched by embedding similarity with a confidence level. The automatic ones are unverified and only for browsing; they never change outcomes.

Clean runs

The two rounds the site compares, thinking off and thinking on, run two requests at a time with the server's prefix cache on. That doesn't change what the model writes (prefix caching is exact), so pass rates, reuse and badges are unaffected, but timings and cache hits reflect a shared, warm server. Cost and latency figures that need to stand alone come from clean mode and are reported separately: runs go one at a time, and the prefix cache is made cold before each one, so nothing cached carries over between tasks that share the same repository and system prompt. The cache is dropped through vLLM's reset endpoint, and the server is fully restarted when it must be (on the first run, and when free host memory runs low). In the prompt v3 round, the thinking-on round itself ran in clean mode. Each run records which method was used.

Blind grading

Tests give the labels. A separate judge adds a view of code quality and never changes them. It never learns how a patch was made (level, prompt, context or tools), and it is limited to read-only tools in a directory outside the project. Up to the v3 round the judge compared every candidate patch for a task side by side and ranked them. From the v4 round the plan is penalty grading: one passing patch at a time, a fixed list of defects, each penalty quoting a line of the patch so the harness can check it.

Scope

One model (Qwen 3.8 27B, FP8 on vLLM), one sample per configuration, server-default temperature. Embeddings come from EmbeddingGemma 2 (the v3 round used Qwen3-Embedding 0.6B). Every configuration runs twice, with thinking off and with thinking on; both rounds keep separate run ids and both appear in the raw data. Clean-mode runs (for cost and latency) have run ids of their own and are reported apart.
