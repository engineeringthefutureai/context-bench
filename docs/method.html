Method

How the experiment works

One model, one set of tasks, one prompt template, and deliberately simple context builders. Only the <context> block is varied from level to level.

The question

When code is written by a model in an existing project, how much does the way its context is built matter? The same model is given the same change requests, and one thing is varied: what is shown of the repository. Each change is checked for correctness, for reuse of the project's existing helpers (instead of their re-implementation), for breakage elsewhere, and for cost.

What the levels are, and what they aren't

Each level is an implementation of one component of a coding harness, the part by which the model's context is built, in its plainest workable form: a fixed list of files, a basic retriever, a short tool loop. None of them should be taken for a fully developed agentic harness by any standard. L7 and L8 are minimal agent loops: only a handful of read-only tools are offered, the budget is capped at 15 calls, and no planning, sub-agents, memory between tasks or code execution are provided. In production assistants, many such components are combined and tuned over years.

That simplicity is intended. The model, the tasks and the prompt are held fixed and one primitive component is swapped, so that the impact of even a primitive implementation of context building on the results can be shown. The numbers should be read as the effect of a context strategy, not as a ranking of products or of complete harnesses.

How coding assistants got their context

Over about six years, the question "what is shown to the model of the code?" was answered in four ways: the open file, retrieved snippets, the whole repository, and agents by which the code is explored. The core idea of one of these moments is reproduced by each level in a simplified form, not the product itself (sources are given in the table below).

The levels

At L0 to L6, the context is built once and the answer is given in one reply. L7 and L8 are minimal agent loops: a small context is given first, and a few tools are used to look around before the answer is given. In prompt v4 (the current round), the file to change is never named: at L1 to L6 it is still shown as the first context block, while at L7 and L8 it has to be found by the agent.

LevelWhat is shown to the model
L0Only the task text (tier-1 control tasks only): the model's behaviour is observed with no repository at all.
L1The target file.
L2The target file, its direct imports and its test file: what would be pasted by hand by a developer.
L3Every source file in the repository, sorted, with paths. On repo L, it can't be fitted into the window: NO FIT.
L4The target file and the top 3 files by retrieval (BM25 or embeddings).
L5The target file and the top 8 functions by retrieval, with path, imports, signature, docstring and body. The task text is used as the query, or up to 5 queries are written by the model in a planning call.
L6The target file and a one-line signature of every function and class (L6+docs: the first docstring line is added).
L7The repository's file tree (line counts, and the number of modules by which each file is imported), with tools offered for at most 15 calls. grep: grep, read_file, find_references. hybrid: semantic_search is added. rich: richer versions of those tools are offered, plus read_symbol (definitions are read by name) and line ranges for read_file. selective: drop is added to rich, by which results no longer needed are removed from the conversation.
L8Experimental. A list of every file with the names defined in it (no signatures). Code can be read only through read_symbol (by name or line range; when a whole file is asked for, its outline is returned). Search tools and drop are offered, along with edit / create_file tools by which the repository copy is changed directly. The budget is set at 15 points, and the points left are shown after each turn.

When a file that doesn't exist yet is created by a change, its path is shown at every level (at L1 to L6 as an empty target block, at L7 and L8 as the same two lines), because a module that doesn't exist yet can't be found by any search. In an ablation arm, reuse_hint, one line is added to the system prompt on L1 and L5: "Prefer reusing existing project helpers over writing new ones." Reuse is never mentioned in the base prompt.

Why each level

At most levels, the way context is built in a real product or a published method is reproduced in simplified form, so that the results say something about strategies actually in use. Two were devised for this experiment: selective dropping in its live-tail form, and L8. The dates given are the first public appearances known.

The minimal agent loop (L7, L8)

A bare-bones loop, far from a production agent: tools are called, the results are read, and an answer is given. Nothing else is done between those steps.

  • A budget of 15 calls is set (L8: 15 points). Half a call is charged for a failed call (bad arguments, an unknown tool), and an error in which the problem is stated is returned; several calls can be made in one turn. At L8, edit, create_file and drop are free, and the edit tools can still be used when the points are spent.
  • In every tool's description, what it takes and returns is stated, never which tool should be preferred. Dead code, decoys and reuse aren't mentioned in any prompt.
  • One more chance is given at the end: one retry is granted for a final reply that is a tool call after the tools were withdrawn, for an answer without a usable <file> block (L8: a run in which nothing was changed), and (L8) for a changed file that no longer parses. Whether a retry was used is recorded for each run.
  • At L8, syntax is checked after every edit (the file is compiled, never run), and a warning with the line is given, much as edits are linted in SWE-agent's interface (Yang et al., 2024); unlike there, the edit is kept, since a change may be made in two steps. No code is run by any tool: a test-running or code-snippet tool was deliberately left out, because arbitrary code could be executed on the host through it, and the hidden tests must never be used as an agent's oracle. The model's code is run by the harness when a run is scored (hidden tests, repository tests, patch coverage), a risk that is accepted for every level.

Rules that keep the comparison fair

  • Only the <context> block is varied. The system prompt, task text, output format, temperature and output-token limit are kept identical at every level.
  • Task text is written in product language, and the needed helper is never named in it.
  • Hidden tests are kept outside the repository and are never put into the context.
  • Context is never truncated silently. A prompt that doesn't fit the model's window is recorded as no_fit, a result in its own right.
  • No agent frameworks are used. Chunking, tokenization, ranking and prompt assembly are the variables under study, so they are owned by the harness.
  • Within its simple design, every level was implemented as well as could reasonably be done, with no thumb put on the scale for or against any strategy.

The repository

shopkit is a synthetic order and inventory service, written for this experiment in three sizes. S is about 2k tokens. M is about 40k tokens and 110 files, written with the standard library only, with its own passing tests. 25 helpers are planted in it (about half are named in words a task would use, half aren't), along with near-miss decoys by which the hidden tests are failed if they are used instead, and dead code named like the canonical place, as is found in real repositories. L is the same shop about a year later: about 169k tokens and 280 files, SQL migrations and HTML templates included. Old code is kept under old names, more dead code is added, and in five live functions of 200 to 270 lines a business rule is buried in the middle. It is too big to be sent whole. The tasks are described on the Tasks page.

What is recorded for each run

Outcome
PASS: a valid answer is given and every hidden test is passed. FAIL: a valid answer is given, but a hidden test is failed. No accepted answer is given in three kinds of runs: UNPARSABLE: code is given, but not in the required <file> blocks. ASKED TO EXPLORE: no code is given; a look at the repository is asked for instead, in prose or as a pretend tool call (which can't be made at a level without tools). NO ANSWER: an empty reply is given (by agents that fell silent, often after the same tool call was repeated). INVALID: anything else, a run from whose reply nothing can be told (a harness failure). The outcome is decided by the reply: an agent with a tool call that failed along the way is still given the outcome of how it ended. OUT OF TOKENS: the output-token limit was hit. NO FIT: the prompt couldn't be fitted into the context window. Infrastructure errors are never recorded; those runs are redone.
Reuse
For reuse tasks, the needed helper is spied on by a hidden test, and whether it is really called by the new code is checked. It is reported apart from correctness, so that "correct but re-implemented" is kept visible.
Regression check
The repository's own tests are run after the patch. Patches by which the hidden tests are passed while code elsewhere is broken or deleted are caught.
Visibility
Whether the needed helper was in the context at all: its definition, its full body, or a call site.
Output protocol
ok, bad_format, no_code or tool_request (exploring was asked for instead of an answer being given).
Cost
Input, cached and output tokens, latency and tool calls.
Badges
Exact ones are read off the run (no code, retried, syntax error in the patch, dead code used, ...), and automatic ones are assigned for what is said in the final answer (completion declared, verification claimed, missing context noted, ...), matched by embedding similarity with a confidence level. The automatic ones are unverified and are meant only for browsing; outcomes are never changed by them.

Clean runs

In the two rounds compared on the site, thinking off and thinking on, two requests are sent at a time, with the server's prefix cache on. What is written by the model isn't changed by this (prefix caching is exact), so pass rates, reuse and badges are unaffected, but timings and cache hits are those of a shared, warm server. Cost and latency figures that have to stand alone are taken from clean mode and reported separately: runs are sent one at a time, and the prefix cache is made cold before each one, so nothing cached is carried over between tasks that share the same repository and system prompt. The cache is dropped through vLLM's reset endpoint, and the server is fully restarted when necessary (on the first run, and when free host memory runs low). In the prompt v3 round, the thinking-on round itself was run in clean mode. The method used is recorded for each run.

Blind grading

Labels are given by the tests. A view of code quality is added by a separate judge, and the labels are never changed by it. How a patch was made (level, prompt, context or tools) is never disclosed to the judge, and it is limited to read-only tools in a directory outside the project. Up to the v3 round, every candidate patch for a task was compared side by side and ranked by the judge. From the v4 round, penalty grading is planned: passing patches are graded one at a time against a fixed list of defects, and a line of the patch must be quoted with each penalty, so that it can be checked by the harness.

Scope

One model is used (Qwen 3.8 27B, FP8 on vLLM), with one sample per configuration and the server-default temperature. Embeddings are produced by EmbeddingGemma 2 (Qwen3-Embedding 0.6B was used in the v3 round). Every configuration is run twice, with thinking off and with thinking on; separate run ids are kept for both rounds, and both are shown in the raw data. Clean-mode runs (for cost and latency) are given run ids of their own and are reported apart.
