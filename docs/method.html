Method

How the experiment works

One model, one set of tasks, one prompt template. Only the <context> block changes from level to level.

The question

When a model writes code in an existing project, how much does the way its context is built matter? The harness gives the same model the same change requests and varies one thing: what it gets to see of the repository. It measures whether the change is correct, whether it reuses the project's existing helpers instead of re-implementing them, whether it breaks anything else, and what it costs.

The eight levels

LevelWhat the model sees
L0The task text only (control tasks only): what the model does with no repository at all.
L1The target file.
L2The target file, its direct imports and its test file: what a developer would paste by hand.
L3Every source file in the repository, sorted, with paths.
L4The target file and the top 3 files by retrieval (BM25 or embeddings).
L5The target file and the top 8 functions by retrieval, with path, imports, signature, docstring and body. The query is the task text, or up to 5 queries the model writes in a planning call.
L6The target file and a one-line signature of every function and class (L6+docs: plus the first docstring line).
L7The target file and tools: grep, list_files, read_file, find_references (hybrid adds semantic_search), at most 15 calls.

An ablation arm, reuse_hint, adds one line to the system prompt on L1 and L5: "Prefer reusing existing project helpers over writing new ones." The base prompt never mentions reuse.

Rules that keep the comparison fair

  • Only the <context> block varies. System prompt, task text, output format, temperature and the output-token limit are identical at every level.
  • Task text uses product language and never names the helper it needs.
  • Hidden tests live outside the repository and never enter the context.
  • Context is never truncated silently. A prompt that doesn't fit the model's window is recorded as no_fit, a result in its own right.
  • No agent frameworks. Chunking, tokenization, ranking and prompt assembly are the variables under study, so the harness owns them.
  • Every level is implemented as well as it reasonably can be, with no thumb on the scale for or against any strategy.

The repository

shopkit is a synthetic order and inventory service written for this experiment, in two sizes: S (about 2k tokens) and M (about 40k tokens, about 110 files, standard library only, with its own passing tests). M has 25 planted helpers, about half named in words a task would use and half not, plus near-miss decoys that fail the hidden tests if used instead, and dead code named like the canonical place, as in real repositories. See Tasks.

What each run records

Outcome
PASS: a valid answer and every hidden test passes. FAIL: a valid answer, but a hidden test fails. INVALID: no accepted answer (no or malformed <file> blocks, pretend tool calls). OUT OF TOKENS: the answer hit the output-token limit. NO FIT: the prompt didn't fit the context window. Infrastructure errors are never recorded; those runs are redone.
Reuse
Reuse tasks have a hidden test that spies on the needed helper and checks the new code really calls it. Reported apart from correctness, so "correct but re-implemented" stays visible.
Regression check
The repository's own tests after the patch. It catches patches that pass the hidden tests while breaking or deleting code elsewhere.
Visibility
Whether the needed helper was in the context at all: its definition, its full body, or a call site.
Output protocol
ok, bad_format, no_code or tool_request (the model asked to explore instead of answering).
Cost
Input, cached and output tokens, latency and tool calls.

Clean runs

In the final round runs go one at a time, and the server's prefix cache is made cold before each one, so nothing cached carries over between tasks that share the same repository and system prompt. The cache is dropped through vLLM's reset endpoint, and the server is fully restarted every 25 runs and whenever host memory runs low. Each run records which method was used.

Blind grading

Tests give the labels. A separate judge adds a view of code quality and never changes them. For each task the judge sees every candidate patch side by side, numbered, with the original repository and a rubric, in a directory outside the project. It never learns how a candidate was made (level, prompt, context or tools), and it is limited to read-only tools.

Scope

One model (Qwen 3.8 27B, FP8), one sample per configuration, server-default temperature. Development ran with thinking off, and the final round reruns everything with thinking on in clean mode. Both arms keep separate run ids, so both appear in the raw data.
