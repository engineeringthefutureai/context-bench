Method

How the experiment works

One model, one set of tasks, one prompt template and a handful of deliberately simple context builders, with only the <context> block changing from level to level.

The question

A model writing code inside an existing project sees only what its harness hands it, so the question is how much that choice matters. To find out, the same model gets the same change requests again and again, and the one thing that changes is how much of the repository the harness shows it. Every resulting change is checked four ways: whether it works, whether it reuses the helpers the project already has instead of quietly re-implementing them, whether it breaks anything elsewhere, and what it cost.

What the levels are, and what they aren't

Each level is one component of a coding harness, the part that builds the model's context, in its plainest workable form: a fixed list of files, a basic retriever, or a short tool loop. None of them should be mistaken for a fully developed agentic harness. L7 and L8 are minimal agent loops with a handful of read-only tools and a cap of 15 calls, and the harness gives them no planning, no sub-agents, no memory between tasks and no way to run code, whereas production assistants stack dozens of such components and tune them for years.

The simplicity is intended: with the model, the tasks and the prompt held fixed, swapping one primitive component shows how much even a crude implementation of context building moves the results. The numbers measure the effect of a context strategy and don't rank products or complete harnesses.

How coding assistants got their context

In about six years, tools found four answers to "what does the model get to see of the code?": first the open file, then retrieved snippets, then the whole repository, and lately agents that go and look for themselves. Each level copies the core idea of one of these moments in simplified form, never the product itself, and the table further down gives the sources.

The levels

L0 through L6 are one-shot: the harness builds the context once and the model answers in a single reply. L7 and L8 are minimal agent loops, in which the model starts from a small context and calls a few tools to look around before it answers. Since prompt v4, the current round, the prompt never names the file to change, so at L1 to L6 the harness still puts that file first in the context, while at L7 and L8 the agent has to track it down itself. The Levels page describes every variant in detail, including how the retrievers rank code and what each agent tool returns.

LevelWhat the model sees
L0The task text and nothing else, on tier-1 control tasks only, to show how the model behaves with no repository at all.
L1The target file.
L2The target file, its direct imports and its test file, which is roughly what a developer would paste by hand.
L3Every source file in the repository, sorted and with paths. Repo L doesn't fit the window, so L3 on repo L is recorded as NO FIT.
L4The target file plus the top 3 files by retrieval, using BM25 or embeddings.
L5The target file plus the top 8 functions by retrieval, each with its path, imports, signature, docstring and body. The retriever searches either with the task text or with up to 5 queries the model writes in a separate planning call.
L6The target file plus a one-line signature for every function and class, and in the L6+docs variant also the first line of each docstring.
L7The repository's file tree, with line counts and the number of modules that import each file, plus tools for at most 15 calls. grep offers grep, read_file and find_references, and hybrid adds semantic_search to them. rich makes those tools richer and adds read_symbol, which reads definitions by name, along with line ranges for read_file. selective is rich plus drop, with which the model clears results it no longer needs out of the conversation.
L8Experimental: an attempt to push the model toward using fewer tokens by allowing it to read only selected parts of a file. The first request gets a compact map of the code base, listing only the symbols and the files they belong to, without signatures. The model can read code only through read_symbol, by name or by line range, and asking it for a whole file returns just the file's outline. For searching, the model has grep, find_references and semantic_search, plus drop for clearing results, and it changes the repository copy directly with the edit and create_file tools. The budget is 15 points, and after each turn the harness reports how many are left.

When a change has to create a new file, the harness shows its path at every level, because no search can find a module that doesn't exist yet: at L1 to L6 it appears as an empty target block, and at L7 and L8 as the same two lines. One ablation arm, reuse_hint, adds a single line to the system prompt on L1 and L5, "Prefer reusing existing project helpers over writing new ones.", while the base prompt never brings up reuse at all.

Why each level

Most levels copy, in simplified form, the way some real product or published method builds context, which keeps the results tied to strategies people actually use. Two were invented for this experiment, selective dropping in its live-tail form and L8, and the dates given are the earliest public appearances known.

L7 selectiveClearing old tool results out of an agent's context, as Anthropic's context editing does (September 2025). The form used here is new: the model can drop only its latest results, which leaves the cached prefix intact, and a sizeable drop earns back part of a call. Recent work by Belcak et al. (November 2026) pushes the same way from the other side, finding that later tokens cost more to generate (up to 7× on frontier open-weight models) and that frontier models lose little or no accuracy when frequent compaction keeps an agent's context short. In their setup the harness compacts the conversation into a lossy recap, whereas here the model picks what to drop and can always read dropped code again.Tests whether the model reads less, without losing what it needs, once it curates its own context, so selective against rich measures the dropping.
L8Established parts put together for this experiment: a symbol index (as in ctags or a language server's workspace symbols), reading by name, and edit tools that replace exact text (as in Anthropic's text editor tool, October 2024, and Aider's search/replace edit format).At L7 (rich, selective) the LLM could read code by symbol and drop it again, yet it kept reading whole files: of about 5,850 agent tool calls, 3,839 were read_file, against 176 for the cheaper read_symbol, which points to a strong pull toward file reading that the model probably picked up in training. L8 takes the whole-file reader away to see what reduced tool access does, so the model can read code only by symbol and changes it with edit tools instead of returning whole files. No gain in quality was expected, since the interest is in token use. L8 is also the one documented exception to "only the context changes", because its output format differs, and it is therefore reported apart from L7.

The minimal agent loop (L7, L8)

The loop is bare-bones and a long way from a production agent: the model calls tools, reads what comes back and answers, and the harness does nothing else in between.

  • The budget is 15 calls, or 15 points at L8. A failed call, such as one with bad arguments or an unknown tool, costs half a call, and the harness answers it with an error that says what went wrong. The model may make several calls in one turn. At L8, edit, create_file and drop are free, and the edit tools keep working after the points run out.
  • Each tool's description says what the tool takes and what it returns, but never which tool to prefer, and no prompt mentions dead code, decoys or reuse.
  • At the end, the harness allows one retry in three cases: a final reply that is a tool call after the tools are gone, an answer with no usable <file> block (at L8, a run that changed nothing), and, at L8 only, a changed file that no longer parses. Each run records whether it used the retry.
  • At L8 the harness checks syntax after every edit by compiling the file, without running it, and sends back a warning with the line number, much as SWE-agent's interface lints edits (Yang et al., 2024). Unlike SWE-agent, the harness keeps the broken edit, since the model might be halfway through a two-step change. No tool runs code: a test-running or snippet tool was left out on purpose, because it would let the model execute arbitrary code on the host, and because the hidden tests must never become an agent's oracle. The harness does run the model's code when it scores a run (hidden tests, repository tests, patch coverage), and that risk is accepted at every level.

Rules that keep the comparison fair

  • Only the <context> block changes, while the system prompt, task text, output format, temperature and output-token limit stay identical at every level.
  • Tasks are written in product language and never name the helper they need.
  • Hidden tests live outside the repository and never enter the context.
  • The harness never truncates context silently: a prompt too big for the model's window is recorded as no_fit, which counts as a result in its own right.
  • No agent frameworks are used, because chunking, tokenization, ranking and prompt assembly are what's being studied, so the harness does all of them itself.
  • Within its simple design, every level was built as well as could reasonably be done, with no thumb on the scale for or against any strategy.
  • The agents (L7, L8) check their answer when they finish: L7 compiles the files in its final answer, and L8 runs the repository's own tests on its edited copy, never the hidden tests. A failure gets one more chance, and the agent isn't told about the check in advance. In the v4 round these checks were added after the runs, by continuing each recorded run whose answer would have failed one from the moment it finished. Nothing earlier in a run changes, so the result is the same as if the checks had been there from the start. That applied to 24 runs, and 17 of them moved from FAIL to PASS.
  • A hidden test found to reject a correct answer gets fixed, and every recorded run is regraded from its saved patch, with no new model calls. That has happened once. On repo L, convention-003's test installed the deployment settings only where a module holds them, so it failed patches that take them as a default argument (settings: Settings = SETTINGS), which is the repository's own majority convention there. With the fix, 11 recorded runs moved from FAIL to PASS, and none moved the other way.

The repository

shopkit is a made-up order and inventory service, written for this experiment in three sizes. S is tiny, at about 2k tokens. M runs to about 40k tokens across 110 files, uses only the standard library and ships with its own passing tests. Planted in it are 25 helpers, roughly half named in words a task would use and half not, along with near-miss decoys, which fail the hidden tests if the model picks one by mistake, and dead code named like the canonical place, the way real repositories tend to look. L is the same shop about a year on, at around 169k tokens and 280 files, now including SQL migrations and HTML templates. Its old code keeps its old names, there is more dead code, and five live functions of 200 to 270 lines each hide a business rule somewhere in the middle, which makes the repository far too big to send whole. The Tasks page lists every task.

What is recorded for each run

Outcome
PASS means the model gave a valid answer that passed every hidden test, and FAIL means a valid answer that failed at least one of them. Three outcomes cover runs with no accepted answer. With UNPARSABLE, the model wrote code, but not in the required <file> blocks. With ASKED TO EXPLORE, it wrote no code and asked to look at the repository first, either in prose or as a pretend tool call, which it can't make at a level without tools. With NO ANSWER, the reply was empty, typically from an agent that went silent after repeating one tool call. INVALID catches the rest, runs whose reply says nothing at all, which points to a harness failure. The reply decides the outcome, so an agent whose tool call failed somewhere along the way still gets the outcome of how it finished. OUT OF TOKENS means the model hit the output-token limit, and NO FIT means the prompt is bigger than the context window. Infrastructure errors never reach the record, because the harness simply redoes those runs.
Reuse
On reuse tasks, a hidden test spies on the needed helper and checks that the new code really calls it. Reuse is reported separately from correctness, so that "correct but re-implemented" stays visible.
Regression check
After applying the patch, the harness runs the repository's own tests, which catches patches that pass the hidden tests while breaking or deleting code somewhere else.
Visibility
Whether the needed helper was in the model's context at all, as a definition, a full body or a call site.
Output protocol
ok, bad_format, no_code or tool_request (the model asked to explore instead of answering).
Cost
Input, cached and output tokens, latency, and tool calls.
Badges
The harness reads exact badges straight off the run (no code, retried, syntax error in the patch, dead code used and so on), and assigns automatic badges from what the model says in its final answer, such as declaring completion, claiming it verified something or noting missing context, matched by embedding similarity with a confidence level. The automatic ones are unverified and meant only for browsing, and they never change an outcome.

Clean runs

The two rounds compared on the site, thinking off and thinking on, ran two requests at a time with the server's prefix cache on. That doesn't change a single token the model writes, because prefix caching is exact, so pass rates, reuse and badges are unaffected, but timings and cache hits come from a shared, warm server. Cost and latency figures meant to stand alone therefore come from clean mode and are reported separately. In clean mode the harness sends one run at a time and makes the prefix cache cold before each, so that nothing cached carries over between tasks that share a repository and a system prompt. It clears the cache through vLLM's reset endpoint and restarts the server outright when it has to, on the first run and whenever free host memory runs low. In the prompt v3 round, the thinking-on round itself ran in clean mode, and every run records which method it used.

Blind grading

The tests set the labels, and a separate judge adds an opinion on code quality without ever overriding them. The judge doesn't learn how any patch was made (level, prompt, context or tools) and works with read-only tools in a directory outside the project. Through the v3 round, the judge put every candidate patch for a task side by side and ranked them. From v4 on, penalty grading replaces the ranking: the judge grades each distinct passing patch on its own against a fixed list of six defects (unrelated changes, re-implemented logic, a broken repository convention, a changed public API, logic that looks wrong where the tests don't reach, and a security or data problem), each worth a fixed number of points. Every penalty has to quote a changed line of the patch, and the harness drops any penalty whose quote isn't one. A patch's points run from 0 to a cap of -40, and they rate the pass without ever turning it into a FAIL. In the thinking-off v4 round, the judge (agy) graded 485 distinct patches, one conversation per task and repository, and every penalty it cited quoted a real changed line.

Scope

One model is tested, Qwen 3.8 27B in FP8 on vLLM, with one sample per configuration at the server's default temperature, and embeddings come from EmbeddingGemma 2 (Qwen3-Embedding 0.6B in the v3 round). Every configuration runs twice, once with thinking off and once with it on, and the two rounds keep separate run ids, both shown in the raw data. Clean-mode runs for cost and latency get run ids of their own and are reported apart.
