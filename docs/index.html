Experiment report · prompt v4 round

How context building affects generated code

One model gets the same 30 coding tasks every time. Only the context changes. The harness builds it in deliberately simple ways, from a single file up to a minimal agent that explores the repository with search tools of its own, and each of those ways is one primitive part of a coding harness. This page reports how far that one choice moved the results in this experiment, and what it cost in tokens.

Reuse

The model reused what it could see

On reuse tasks a hidden spy watches whether the new code calls the helper the task needs, and each bar groups those runs by how much of the helper sat in the model's context when it answered.

With the full source in view, the model reused the helper in 95% of runs. With thinking, a bare signature worked almost as well (91%), and without thinking it fell to 40%. With nothing of the helper in view, the model wrote its own, except in 3 runs that guessed a conventional name from a visible module, the task's wording or the reuse hint (Case studies). The agents nearly always found the helper, so their reuse came close to 100%.

Quality

How clean the passing code is

A blind judge, Gemini 4 Neon in Google Antigravity (agy), read every passing patch. It never learned which level produced a patch, and it flagged what tests can't see: unrelated edits, re-implemented helpers, broken conventions, logic that looks wrong where no test reaches, and risky code. A clean pass clears the hidden tests, leaves the repository's own tests green and draws no flag from the judge.

Regressions

Passing the hidden tests while breaking the repository's own

After every run, the harness also ran the repository's own test suite on the patched copy. A run whose answer cleared every hidden test but left at least one of the repository's original tests failing, unable to import or gone is labelled BROKE KNOWN TESTS, and it doesn't count as a pass anywhere on this site. On these tasks that happened in 13 of 1373 runs that cleared the hidden tests (3 with thinking off, 10 with thinking on, 0 with Gemini). The runs split by whether the model had the broken test in front of it: a test counts as seen when its code (its definition and the start of its body, not just its name in a signature map) appeared in the prompt or in a tool's output at any point in the run.

Reference

A commercial agent harness as the baseline

L-AG served as a baseline of what a complete agent harness achieves on these tasks. It runs Google's Antigravity, a commercial product with many thousands of hours of development behind it: its own system prompt, its own tools, shell commands included, and its own loop. The primitive levels on this page are harnesses put together in a few days for this experiment.

For the baseline, Antigravity was paired with Gemini 3.5 Flash-Lite, one of the cheapest Gemini models. These 30 tasks are a simple test suite, well below the level at which frontier models are benchmarked today, so a small, inexpensive model was enough to show what the harness itself contributes. The same harness also ran with Qwen 3.8 27B, the model under study everywhere else.

The pairing of Antigravity and Gemini showed a high synergy. None of Gemini's 823 shell commands ran empty, and the pair passed 54 of 57, though it didn't reach every task: it missed long-004@L, reuse-008@L, reuse-010@M. Qwen in the same harness often named tool arguments in its own style, which Antigravity ignores, so many of its commands ran nothing (the Levels page has the details).

The primitive harnesses paired with a mid-size local model held their own. On these tasks, L8 with Qwen passed 55 of 57 and L7 selective 53, on less input per run than either Antigravity pairing.

Wall-clock times can't be compared: Gemini ran on Google's hosted API, six runs at a time, while Qwen ran on two local GPUs, two at a time. Every pairing ran one sample per task.

Side experiment

Qwen's own tool names

A side arm, thinking off only, gave the agents' tools the names and parameters of Qwen Code, Qwen's own coding agent (read_file(file_path, offset, limit), grep_search, edit(file_path, old_string, new_string), write_file). Limits

How certain the results are

  • One model and one sample per configuration. Repeating a run flips about 1 outcome in 5, roughly ±3 per 30 runs, so a gap of a few runs between two configurations means little. The gaps between context levels on this page are many times that size.
  • All tasks run on one synthetic shop service, in three sizes, written for this experiment so the model can't have seen it before. Real repositories are messier.
  • The judge is a model too. Its findings rate how clean a passing patch is, and PASS or FAIL comes from the tests alone.
