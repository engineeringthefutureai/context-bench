context-bench · development round

Eight ways to give a model a codebase

The same 20 coding tasks were given to Qwen 3.8 27B eight times over, and only the way its context was built was changed, from the bare task text up to an agent that greps the repo itself. Reported below are the factors by which the results were moved, the cost of each level, and how the expectations held going in were borne out.

Summary

Results were decided by whether the helper's code was shown and whether it could be checked

Nearly every result in this round is explained by two questions about the context. Was the needed helper's code placed in front of the model? And could what was shown be checked against the rest of the repo? Both are answered yes by L3 and L7, and the top two places are taken by them. In the search contexts (L4, L5) the helper is included about half the time and no means of checking is offered, so the middle is occupied by them, and every patch in which dead code was imported was produced by them or by L6. In L6, names are listed without bodies. The wanted helper is spotted, the need to read it first is announced, and the reply is ended there, since no file is handed over in a single-shot run.

Setup

The prompt and tasks were held fixed while eight context blocks were tried

Between levels, only the <context> block was changed. A general senior-engineer brief is used as the system prompt, reuse is never mentioned in it, and the task text and output format were kept fixed. Tasks are run against shopkit, a made-up Python shop that was written for this purpose so that it could not have been met in training. Two sizes are provided. S is about 2k tokens. M is about 41k, and 25 helpers, lookalike decoys and dead code that is marked as dead nowhere are hidden in it. Pass or fail is decided by hidden tests kept outside the repo, and on reuse tasks a spy test is used to check that the existing helper is really called by the new code.

Hypotheses

Expectations held going in

Some of these were taken from the design notes. The rest were assumed while the levels were being built. Each verdict is limited to this round, which was run with thinking off and one run per configuration.

Findings

What was shown by the runs

1

Reuse was determined by whether the helper's code was visible

When the helper's source was included in the context, the helper was used in 85% of runs. When nothing of it was included, 2% was reached. Almost the same effect is produced by a call site as by the definition, because the import seen elsewhere is copied. With a bare signature, 19% was reached.

2

The limits of each level were reached at different kinds of task

A reuse task is hinged on one helper, and one helper can be found by search reasonably well. In convention tasks, errors must be raised, events published or settings loaded in the way it is done in the rest of the shop. In cross-file tasks, one feature is spread over the order model, fulfillment and the API. For both kinds, reading around the repo is required. This was managed best by L3 (6 of 8) and by L7 (14 of 16 in its first sample, 10 of 16 in the rerun), and mostly not by the search levels, whose pass rates were dropped to 25-40%.

3

The whole-repo result was nearly matched by the agent on a quarter of the fresh input

On repo M, 85% was passed by L3, and 65-80% by the two agent variants over two samples. About 42k tokens are sent by L3 on every run. About 48k are sent by L7 across all its turns, but the previous prompt is resent with each turn, so only around 11k is new and the rest can be billed at the cached rate. L3 can no longer be used once the window is outgrown by the repo. The size of the repo makes no difference to L7. The cost is paid in time instead: roughly 100 seconds are taken per run, against 29 for L3.

4

Results were improved by model-written queries and barely by a change of engine

When the task text is used as the query, helpers named like the task wording are found by both BM25 and embeddings, and the oddly named ones are missed by both. No words, and little meaning, are shared between "Product codes must be cleaned up the same way as everywhere else" and normalize_sku. When one planning call is given to the model so that its own queries can be written ("clean product code SKU normalization"), that helper is ranked #1 by the embedder.

5

Harm was done by decoys only when they could not be checked

Dead lookalikes were imported by five patches: sku_code, cleanSKU, slugify, and kgToLbs twice. All five were failed, and every one was produced by a single-shot context built by embedding search or the L6 map. In L3 it can be seen that the dead modules are imported only by their own old tests. In L7, list_files with import counts and find_references for usages are provided, and each time a dead file was opened by the agent, which happened a handful of times, it was left alone. No harm is done when a decoy is surfaced by search. Problems arise when a choice has to be made with nothing to verify it against.

6

Results were made worse by a map of signatures

In L6, every function signature in the repo is listed, by which the helper should be made easy to find. A pass rate of 11% was reached. The helper is found. Then it is announced that the helper must be read first and the reply is ended, or a tool call is written that will never be run. Of L6's 48 failures, 33 are broken replies of this kind:

"I need to understand how the shop rounds percentage amounts. Let me look at the relevant files."

7

The stale docstring was fixed only by the agent

In trap-001, a pound option is documented for format_weight(grams, unit) that is no longer implemented by its body. The function should be reused and repaired by the right patch. This was done in one run out of 15, by L7 with grep. In the L7 rerun the drift was fixed by both agent variants.

In an earlier thinking-on sample the drift was also caught by L3, after 6.2k thinking tokens had been spent. The docstring was trusted by L6+docs after 1.6k. In every run in which it was handled correctly, the function body was in view.

8

Single-shot runs were hurt by thinking off, and the agent was left unaffected

With thinking off, the model behaves as if it had been placed inside an agent harness. Replies are opened with "I'll explore the codebase..." and tool calls are written that are never executed. On L0-L3 a high price was paid for this. 9 of 31 runs were passed with thinking off and 20 of 31 with it on, and most of the gap was caused by broken output. In L7 the tool calls are executed, and the two settings were tied at 11 of 13. The full 15-call budget and twice the input were used with thinking off, while about 7 times as much output was written with thinking on. Turning thinking off for coding harnesses is often recommended by people who run Qwen locally, and that advice is supported by these numbers wherever a real tool loop is present.

9

The job was done by a general-purpose prompt

Three system prompts were tried on the same 74 configurations. 18 were passed with the original. 23 were passed with a detailed one in which capabilities and output rules were listed. 27 were passed with a plain senior-engineer brief in which the job is described and no hints about this benchmark are given, and the number of replies without code or with requests for tools was reduced from 36 to 7. Reuse, helpers, docstrings and dead code are never mentioned in the final prompt. An explicit reuse hint was also tried as an ablation, and no improvement was produced. At L1, 1/20 was passed with it and 5/20 without. At L5, 15/27 was reached against 14/27.

Blind review

Agreement with the tests was shown by the judge, and a gap in them was exposed

For each task, every distinct patch was shown to a Claude Code judge side by side with the original repo, without any indication of how it had been produced, and the patches were ranked. On average, passing patches were placed in the top fifth and failing ones near the bottom. A reuse score of 4.7 out of 5 was given on average where the spy test was passed, and 1.8 where it was failed.

In 5 of 306 runs, the tests were contradicted by the judge. Two patches were failed because of a single slip in otherwise good code. The other three were passed by the tests despite being bad code, and a gap in the harness is exposed by one of them.

  • cross-002, L5 was passed although pick_list, packing_slip and two serializers had been deleted and # lines 11-19 placeholders had been left behind. Code outside the task is never examined by the hidden tests.
  • convention-001, L4: Stock was rewritten with a lock and a global decimal context, far beyond what had been asked by the task.
  • reuse-001, L4: $ was hard-coded instead of format_money being called, so EUR invoices would be broken.

One stored score is wrong. In one patch's note its scores were revised by the judge, but the stored correctness of 5 was never updated.

Analysis

The levels are sorted by two questions

When the findings are placed side by side, the levels are seen to fall along two axes. Was the helper's code contained in the context? Could what was given be checked? Most outcomes are predicted by those two answers, and much of the remainder is accounted for by the broken replies caused by thinking off.

For practical use. When the repo fits in the window and the prefix cache is warm, pasting all of it (L3) is the simplest strong option, and here it was also found to be the fastest. When the repo is too large, or input tokens are paid for, nearly the same quality is held by an agent equipped with plain read-only tools (grep, read, a file list with import counts, find references) on about a quarter of the fresh input. The shop's conventions were also followed best at that level, and the stale docstring was fixed only there. Retrieval is worthwhile mainly when the queries are written by the model. A signature map should not be used in a single-shot setup at all.

Three results were unexpected. L6 was ranked last even though every helper's name is shown in it. No improvement over BM25 was achieved by embeddings alone. And L3 was not found to be perfect: on the larger repo 85% was passed, and two convention runs and the trap were missed.
